# Requirements Document

## Introduction

The Private Event Eligibility Pass (PEEP) is a privacy-preserving event access system built on the Midnight Network. It allows participants to prove eligibility to enter an event (e.g., "I am a student") without revealing unnecessary personal information such as their name, student ID, college, email, or phone number. The system issues a digital event pass backed by a zero-knowledge proof, which an event organizer can verify and mark as used — preventing replay. The core principle is: **VERIFY ELIGIBILITY, NOT IDENTITY.**

## Glossary

- **System**: The Private Event Eligibility Pass (PEEP) smart contract and frontend dApp.
- **Participant**: A person who wishes to attend an event and must prove eligibility.
- **Organizer**: An entity that creates events and verifies passes at entry.
- **Scanner**: Staff or software used by the Organizer to verify and mark passes at entry.
- **Event**: A named occurrence with a unique ID and an eligibility requirement.
- **Event ID**: A unique public identifier for an Event.
- **Eligibility Requirement**: A condition a Participant must satisfy to receive a Pass (e.g., must be a student).
- **Private Credential**: A Participant's private personal data used to prove eligibility (e.g., student ID hash). Never stored on-chain.
- **Eligibility Witness**: A private input to the eligibility circuit derived from the Participant's Private Credential.
- **Eligibility Circuit**: A zero-knowledge circuit that verifies the Eligibility Witness satisfies the Eligibility Requirement without revealing the witness.
- **Pass**: A digital token issued to an eligible Participant, linked to a specific Event, with active/used status.
- **Pass ID**: A unique public identifier for a Pass.
- **Pass Status**: The current state of a Pass — ACTIVE or INVALID.
- **Entry Status**: Whether a Pass has been used for entry — NOT_USED or USED.
- **Compact**: The smart contract language used on the Midnight Network.
- **Ledger State**: Public on-chain data managed by the Compact contract.
- **Private State**: Off-chain private data known only to the Participant and the proof system.
- **disclose()**: A Compact built-in that moves a value from private to public context.
- **ZK Proof**: A zero-knowledge proof generated by the eligibility circuit.
- **Lace Wallet**: The browser wallet used to connect to the Midnight Network.
- **QR Code**: A machine-readable code encoding the minimum data needed to verify a Pass.
- **Replay Attack**: An attempt to use an already-used Pass a second time to gain entry.
- **Proof Server**: A local service that generates ZK proofs for contract transactions.
- **Indexer**: A Midnight network service that indexes on-chain state for querying.

## Requirements

### Requirement 1 — Eligibility Verification

**User Story:** As a Participant, I want to prove I am eligible to enter an event using a private credential, so that I can receive an event pass without revealing my personal identity.

#### Acceptance Criteria

1. WHEN a Participant submits a valid Eligibility Witness to the System, THE System SHALL verify the witness satisfies the Eligibility Requirement and produce a public eligibility result of ELIGIBLE without exposing the Eligibility Witness in the Ledger State.
2. WHEN a Participant submits an invalid Eligibility Witness to the System, THE System SHALL reject the eligibility verification and produce no Pass.
3. WHILE a Participant's eligibility verification is in progress, THE System SHALL keep the Private Credential and Eligibility Witness in Private State only and SHALL NOT include them in the Ledger State.
4. WHEN eligibility verification succeeds, THE System SHALL record only the minimum required public data: the Event ID, the Pass ID, Pass Status, and Entry Status.
5. IF a Participant provides an Eligibility Witness that does not match the Eligibility Requirement hash, THEN THE System SHALL reject the transaction with an error indicating ineligibility.

---

### Requirement 2 — Event Management

**User Story:** As an Organizer, I want to define events with unique IDs and eligibility requirements, so that only eligible Participants can receive passes for each specific event.

#### Acceptance Criteria

1. THE System SHALL maintain a unique Event ID for each event in the Ledger State.
2. THE System SHALL store the eligibility requirement as a public commitment hash in the Ledger State so verifiers can confirm which credential type is required without learning individual Participant data.
3. WHEN an event is created, THE System SHALL set the event status to ACTIVE in the Ledger State.
4. IF a Participant attempts to obtain a Pass for an event that does not exist or is not ACTIVE, THEN THE System SHALL reject the transaction.

---

### Requirement 3 — Event Pass Issuance

**User Story:** As a Participant, I want to receive a digital event pass after proving eligibility, so that I can present it at the event entrance.

#### Acceptance Criteria

1. WHEN eligibility verification succeeds for an event, THE System SHALL issue a Pass with a unique Pass ID linked to the Event ID.
2. WHEN a Pass is issued, THE System SHALL record Pass Status as ACTIVE and Entry Status as NOT_USED in the Ledger State.
3. WHEN a Pass is issued, THE System SHALL NOT include the Participant's name, email, phone, student ID, college name, or any other personal identifier in the Ledger State.
4. THE System SHALL associate each Pass with exactly one Event ID in the Ledger State so that a Pass cannot be used for a different event.

---

### Requirement 4 — One-Time Entry and Replay Protection

**User Story:** As an Organizer, I want each pass to be usable only once, so that Participants cannot gain multiple entries using the same pass.

#### Acceptance Criteria

1. WHEN a Scanner verifies a Pass with Entry Status NOT_USED and Pass Status ACTIVE, THE System SHALL transition the Entry Status to USED in the Ledger State.
2. WHEN a Scanner attempts to verify a Pass with Entry Status USED, THE System SHALL reject the transaction and return a PASS_ALREADY_USED error.
3. WHEN a Scanner attempts to verify a Pass with Pass Status INVALID, THE System SHALL reject the transaction and return an INVALID_PASS error.
4. THE System SHALL enforce Entry Status transitions in the Ledger State so that the replay protection cannot be bypassed by frontend-only logic.
5. WHEN a Scanner verifies a Pass for an Event ID that does not match the Pass's recorded Event ID, THE System SHALL reject the transaction and return a WRONG_EVENT error.

---

### Requirement 5 — Privacy Model

**User Story:** As a Participant, I want my personal information to remain private throughout the eligibility and entry process, so that my identity is protected even from the event organizer.

#### Acceptance Criteria

1. THE System SHALL store only Event ID, Pass ID, Pass Status, and Entry Status as Ledger State; all other data SHALL remain in Private State.
2. WHEN a ZK Proof is generated, THE System SHALL use disclose() only to move the eligibility result (a boolean) and the Pass ID to the Ledger State, and SHALL NOT disclose the Eligibility Witness or Private Credential.
3. WHEN a QR Code is generated, THE System SHALL encode only the Pass ID and Event ID, and SHALL NOT encode the Participant's name, student ID, email, phone, college, or Eligibility Witness.
4. THE System SHALL NOT log Private Credential data or Eligibility Witness data to any public output, browser console, or transaction metadata.

---

### Requirement 6 — Pass Verification UI

**User Story:** As a Scanner, I want to scan or enter a QR code to verify a pass, so that I can grant or deny entry quickly.

#### Acceptance Criteria

1. WHEN a Scanner submits a Pass ID for verification, THE System SHALL display Pass Status, Entry Status, and the associated Event ID.
2. WHEN a Pass is ACTIVE and NOT_USED, THE System SHALL display an ACCESS GRANTED result with Entry Status NOT_USED.
3. WHEN a Pass Entry Status is USED, THE System SHALL display PASS ALREADY USED and deny entry.
4. WHEN a Pass ID is not found or is invalid, THE System SHALL display INVALID PASS.
5. WHEN a Pass is valid but belongs to a different Event ID than the one being verified, THE System SHALL display PASS NOT VALID FOR THIS EVENT.
6. THE System SHALL NOT display the Participant's Private Credential, name, student ID, email, phone, or college in any verification result shown to the Scanner.

---

### Requirement 7 — Wallet Integration

**User Story:** As a Participant, I want to connect my Lace wallet to the dApp, so that I can sign transactions for eligibility verification and pass issuance.

#### Acceptance Criteria

1. WHEN a Participant connects a Lace wallet, THE System SHALL display the shortened wallet address and a connected status indicator.
2. WHEN a wallet is not available, THE System SHALL display a wallet unavailable message and a link to install the Lace wallet.
3. WHEN a Participant rejects the wallet connection, THE System SHALL display a connection rejected message and allow retry.
4. WHEN a Participant is on the wrong network, THE System SHALL display a wrong network message specifying the required network.
5. WHEN a Participant disconnects the wallet, THE System SHALL clear the session state and return to the disconnected state.

---

### Requirement 8 — QR Code Generation and Security

**User Story:** As a Participant, I want a QR code generated from my event pass, so that the Scanner can verify my entry without requiring me to interact with the blockchain directly.

#### Acceptance Criteria

1. WHEN a Pass is issued, THE System SHALL generate a QR Code containing only the Pass ID and the Event ID.
2. THE System SHALL NOT encode the Participant's Private Credential, Eligibility Witness, name, email, phone, student ID, or college in the QR Code.
3. WHEN a QR Code is scanned by the Organizer's verifier, THE System SHALL use the Pass ID and Event ID from the QR Code to query the Ledger State for the current Pass Status and Entry Status.
4. WHERE a QR Code reader is available in the browser, THE System SHALL support camera-based QR scanning in the Organizer verification UI.

---

### Requirement 9 — Pretty-Printing and Serialization

**User Story:** As a developer, I want pass and event data to be serializable and deserializable consistently, so that QR codes, API responses, and on-chain state can be round-tripped without data loss.

#### Acceptance Criteria

1. WHEN a Pass record is serialized to JSON for QR Code generation, THE System SHALL produce a JSON string containing Pass ID and Event ID.
2. WHEN a JSON string produced by the Pass serializer is deserialized, THE System SHALL produce an object equal to the original Pass record.
3. WHEN an on-chain ledger state record is read by the frontend, THE System SHALL parse it into a typed TypeScript object equivalent to the original ledger state.

---

### Requirement 10 — Error Handling

**User Story:** As a Participant or Scanner, I want clear, actionable error messages for all failure states, so that I understand what went wrong without exposing private information.

#### Acceptance Criteria

1. WHEN a transaction fails due to wallet rejection, THE System SHALL display a user-readable message: "Transaction rejected by wallet."
2. WHEN a transaction fails due to an invalid eligibility proof, THE System SHALL display: "Eligibility verification failed. Please check your credential."
3. WHEN a transaction fails due to a network error, THE System SHALL display: "Network error. Please try again."
4. WHEN an error occurs, THE System SHALL NOT include the Participant's Private Credential, Eligibility Witness, or any private data in the error message.
5. WHEN a proof generation fails, THE System SHALL display: "Proof generation failed. Ensure the proof server is running."
